## Prioritized opportunities

### 1. Bound Cram's forgotten-history work — high priority

Evidence: `packages/backend/convex/model/cram.ts:91` collects every Again log for the library in a window of up to 365 days, then builds a unit-ID set. Both `cram.count` and `cram.queue` call the selector (`cram.ts:66,83`). Even a tiny selected deck reads other decks' matching history. A date window is not a row bound, and imported history can be large.

Opportunity: maintain a compact latest-Again timestamp per unit, or query an indexed unit/rating history boundary rather than collecting all logs. Maintain exact semantics across undo, imported history, moved cards, and deletion. A simple limit would silently change matches and is not an acceptable fix. Also separate count/eligibility selection from content hydration.

Validate: fixed deck with constant unit count and growing Again history, including history in unrelated decks. Record rows/bytes read and count/queue latency; verify identical membership after undo, move, and import. This is a source-confirmed unbounded read, not an observed production failure.

### 2. Replace statistics history scans with compact aggregates — high priority

Evidence: `packages/backend/convex/stats.ts:27,58,100,169` reads up to 20,000 review logs and separately up to 20,000 cram logs. Overview also reads up to 2,000 authored cards and two sets of up to 10,000 review units (forecast and state totals). The arithmetic ceiling is approximately 62,000 row-read requests before access/deck reads, above the repo's documented 32,000-document transaction allowance. Overlapping unit reads may be accounted differently; either history stream plus the other can alone exceed that allowance. These caps are not a shared transaction budget. The compact homepage heatmap uses the same history helpers.

A deck filter is applied after reading library-wide history, so another deck's activity still costs work and can consume the truncation budget. Full card content is loaded merely to construct an ID set; full unit front/back content is loaded for numerical statistics.

Opportunity: daily study aggregates for activity and retention, lightweight state totals, and a forecast read of scheduling metadata only. Preserve account-timezone day boundaries, undo, deletion, moved-card history, and imports. At minimum avoid reading forecast units separately from a complete scoped unit set when both are required. Decide how aggregates handle timezone changes before implementation.

Validate: small/near-cap libraries, both log streams above 20,000 within the window, sparse single-deck selection, and imported history. Measure total transaction rows/bytes, latency, and exactness versus an offline reference. Aggregates can improve completeness as well as cost; current truncation is surfaced to clients.

### 3. Make always-mounted navigation cheaper — high priority

Evidence: `apps/web/src/components/app-sidebar.tsx:365,435` subscribes to `review.status` and `decks.list`. `decks.ts:37,73` uses `selectSession` per deck despite existing deck counters. `review.ts:67` separately selects a whole-library session for status. `model/queue.ts:121,170` fetches full eligible units, partitions and sorts them, and selects Frontier candidates. `nextDueAfter` adds a per-deck future scan. Thus unrelated pages still carry due-selection work, and a rating can invalidate multiple selectors. The homepage uses the same deck-list query key, which can share that subscription; it is not another independent list request merely because two components use it.

Opportunity: a navigation-specific deck list containing names, slugs, pin state, and lightweight counters; reserve full deck stats for screens needing them. Consider one compact eligibility result supplying global badge and per-deck counts, with exact existing budget semantics. Start with the library-wide due index already present in `schema.ts:287` to assess whether status can avoid the serial per-deck query fanout. Account for pending deleted-deck cleanup before using it.

Validate: one-deck versus 200-deck libraries with equal total units, empty decks, many due units, and capped daily budgets. Measure reads and rating-to-next-prompt latency with Browse, Stats, and Graph recently visited. Do not assume per-deck counts sum to the global count: current selection applies account-wide budgets separately to the selected scope.

### 4. Bound review queue hydration and payloads — medium/high priority

Evidence: `review.ts:28` returns every selected item; `model/queue.ts:9` resolves cards and decks sequentially, caching each distinct document within the call. Each returned item includes parsed authored content plus generated front/back text. Unlimited daily review settings can admit a large backlog. `cram.queue` explicitly returns every matching unit and lets the client shuffle and limit. Siblings can repeat the same authored content in many items.

Opportunity: separate ordered eligibility IDs/versions and counts from a small current/next content window; deduplicate flashcard content within a response. Move Cram's final selection limit into the backend while preserving the intended randomization. Use bounded parallelism for independent hydration only after read-volume and payload changes; parallelism alone saves no database bytes.

Validate: 10,000 due units, long cloze content, and 60 sibling units on one card. Measure serialized result bytes, reads, time to first prompt, and rating-to-next-prompt. Preserve stable admission, sibling handling, bury/undo, and the rule that an already admitted card stays answerable after a budget changes.

### 5. Align mobile subscriptions with the event-driven study clock — medium priority, small scope

Evidence: `apps/mobile/src/App.tsx:151` advances `now` every 30 seconds. Both deck list and queue receive that argument; while mounted this creates about 120 argument changes per hour for each query, even without a write or newly due card. Web already schedules clock advances from `review.status.refreshAt` in `apps/web/src/lib/study-clock.ts`.

Opportunity: use next-due/day-boundary scheduling on mobile, with foreground catch-up and background timer/subscription handling. The mobile client is currently a smoke screen, so avoid investing in a large rendering refactor before the full mobile UX exists. Its ScrollView mounts all deck rows; a virtualized list becomes appropriate when building the full deck screen.

Validate: idle foreground session, background/resume, study-day rollover and a newly due card. Compare query argument changes, backend executions, and stale-count behavior. The 120/hour figure is arithmetic from the timer, not a measured production execution count.

Consider authenticated thumbnails/responsive variants and stored dimensions; keep the current study prompt's image eager and defer offscreen images. Validate image transfer bytes, decode time, layout shifts, and zoom quality.

### 7. Audit query clock/cache use — medium priority

Evidence: time-dependent queries accept a client `now` but compute using `Date.now()` instead (`review.ts`, `decks.ts`, `stats.ts`). Web's explicit timer handles time-driven refresh, so this is not a claim that all counts fail to refresh. However, Convex documents that query wall-clock reads can reduce cache reuse. Each mobile timer argument also creates a distinct query identity.

Opportunity: explicitly separate the cacheable display timestamp from server-owned mutation time. Investigate whether queries can use a validated/coarsened display clock while ratings continue to use trusted server time. Do not mechanically substitute the browser clock in scheduling or eligibility checks. Measure cache reuse before changing the contract.

### 8. Secondary scale work — lower priority under current caps

- Filtered Browse: `flashcards.ts:276,308,339` applies substring/tag/state tests after selecting sort streams, and filtered counts collect summaries. Pagination bounds returned cards, not necessarily all candidates inspected. Measure rare/no-match search on 2,000 cards before considering a search index; full-text token search would change current substring semantics.
- Summary rebuilds: `model/summaries.ts:228` reads all sibling units when a touched card's summary is rebuilt. This is bounded to 60 siblings; profile long cloze cards before replacing the simple, atomic implementation.
- Revision contention: `model/study.ts:131` updates a library-wide revision document for study writes; Graph reads that revision. Concurrent writers may contend and Graph may rerun for unrelated changes. This is a hypothesis until OCC/retry data confirms it. Do not shard the revision blindly: export snapshot checks and graph/assistant write version checks rely on its exact meaning. The revision is already separate from the library access document, avoiding a broader auth-read invalidation problem.

## What already helps

Browse uses summary indexes, cursors, counters, and a virtualized tile grid. Graph layout and Anki conversion run in workers. The editor and equation renderer load on demand. Web clock refreshes follow due events rather than a fixed interval. Heavy unused subscriptions expire after 30 seconds, while ordinary ones remain for five minutes (`lib/queries.ts`). Do not remove these protections or add blanket memoization/caching without a measured benefit.

## Suggested execution order and measurement plan

First establish reproducible measurements for Cram, statistics, sidebar/status, and queue hydration. Use small and near-cap libraries, dense/sparse due dates, long content, many decks, and long imported history. Hold input data, network/device conditions, cache state, and route sequence constant across repetitions. Capture median and p95 query/rating-to-prompt times, rows/bytes read, payload size, and active subscriptions. Use production read-only Convex insights when available to determine which suspected costs actually occur.

Then fix unbounded history selection and statistics transaction headroom. Next reduce navigation/queue work. Mobile clock alignment can be a separate small improvement. Profile editor and image paths before changing their implementation. Keep an optimization attempt ledger with before/after measurements, variance, and a keep/revert verdict. Use the existing manual QA workflow; repository instructions prohibit adding test suites.

No web-vitals/PerformanceObserver collection was found in the searched app/package source. Graph timing marks exist but are development/E2E-only (`lib/graph-perf.ts`). Add narrowly scoped field measurements if production prioritization is needed; do not transmit card text or private content. Initial provisional experience targets can use LCP ≤2.5 s, INP ≤200 ms, and CLS ≤0.1, with backend budgets chosen from measured baselines.
