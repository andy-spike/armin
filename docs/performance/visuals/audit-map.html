Queries, validation, and correctness constraints

cram.count and cram.queue both call selectCramUnits. Its forgotten filter reads library-wide logs before matching the selected deck. stats.overview and stats.heatmap also read library-wide history before applying deck membership. Their separate read caps do not guarantee a safe combined transaction budget.

Measure: rows/bytes read and query latency while increasing history with a fixed card count. Repeat with a small deck inside a busy library.

Preserve undo, imports, moved-card history, deletion, and timezone behavior. Do not simply truncate Cram logs: that could exclude valid matches.

Why one rating can trigger more work

Live queries rerun when data they read changes. The sidebar stays mounted across pages, so broad reads can add work even while another screen is open. Identical query keys can share a subscription; the opportunity is reducing distinct selectors and their read sets.

Measure: backend reads with 1 versus 200 decks at the same total unit count; then measure rating-to-next-card latency.

Keep daily review limits and new-card selection exact. Per-deck counts cannot simply be summed to get the global count.

Where the savings could come from

Large backlogs and cloze siblings can repeat authored content across many queue items. Smaller content windows could reduce reads, response bytes, and first-prompt delay.

Measure: response bytes and time to first prompt with 10,000 due units, long text, and cloze siblings.

Preserve stable admission, sibling grouping, bury/undo, and answers to already admitted cards. For Cram, preserve randomization when moving the selection limit to the server.
