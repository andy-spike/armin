## 1. Stored table plus paragraph was dropped by the card editor

**Repro before the fix.** A stored basic card with back
`| A | B |\n| --- | --- |\n| 1 | 2 |\n\nAfter table.` opened from Browse
showed only `After table.` in the rich editor. Saving then replaced the stored
back with the visible paragraphs, permanently deleting the table. The same
happened with a paragraph before the table and with a table-only field (the
round-1 fallback only ran when the parsed document had no nodes at all).

**Root cause.** `@tiptap/markdown`'s parser has no table handler. `marked`
emits a `table` token, `parseFallbackToken` has no `tokens` for it, and the
parser returns `null` for that token while keeping the surrounding paragraphs.
The editor therefore had a valid, non-empty document and never used the
literal-text fallback. `editor.getMarkdown()` then wrote the document back
without the table.

**Change** (`apps/web/src/components/ui/markdown-editor.tsx`):

- The editor now tokenizes the initial source through the same `marked`
  instance the Markdown extension uses, walking `tokens`, `items`, `header`,
  and `rows` recursively. A `table` token or a block `html` token selects a
  plain-text editing mode (a textarea) for that field instead of the rich
  editor. If tokenization throws, the field also stays in plain-text mode.
- Plain-text mode binds the textarea directly to the stored string, so an
  unedited field is never rewritten, and edits to any other part of the text
  keep the table source. `Add image` still works there and inserts a portable
  `armin-media:` Markdown reference at the caret.
- The editor no longer parses the initial value before `onCreate`; detection
  runs first, so the rich editor never sees a table it would drop. An
  externally supplied value is checked again before it is loaded.
- Read-only rendering already handled tables through `react-markdown` +
  `remark-gfm` and the existing `.markdown-content table` styles, so
  `markdown-content.tsx` needed no change. Verified in review below.

**Verification.**

- `screenshots/table-editor-fallback.png`: the Back field opens in plain-text
  mode with the exact stored source and the note that saving preserves it.
- Three fresh cards (table only, table + paragraph, paragraph + table +
  paragraph) were opened from Browse and saved unedited. The API values before
  and after were byte-identical; see `table-roundtrip.txt` and
  `table-roundtrip-{before,after}.json`.
- Appending ` extra` to the table-plus-paragraph card saved
  `| A | B |\n| --- | --- |\n| 1 | 2 |\n\nAfter table. extra`; the table was
  preserved.
- `screenshots/table-review-render.png` shows the same card in review with a
  real two-row HTML table (`A | B` / `1 | 2`), confirming read-only rendering.
- An ordinary basic card still opens in the rich editor (`contenteditable`
  front and back with the expected text), so the fallback is limited to fields
  the schema cannot represent.

## 2. Rating shortcut chips below AA

**Measured before** (compositing `bg-on-accent/10` over each button): light
Hard 3.97, light Good 3.87, dark Again 3.94, dark Easy 4.13.

**Root cause.** The chip background was a translucent copy of the *text*
colour. In light mode that lightened the button background under paper text;
in dark mode it darkened the background under black text. Both reduced
contrast.

**Change** (`apps/web/src/components/review-session.tsx`):

- The chip now uses `bg-ink/10` (a dark overlay in light mode, a light overlay
  in dark mode), which increases contrast instead of reducing it. The Show
  answer chip uses the same treatment.
- Dark hover shades were changed to lighter tints (Again `#e0655a`, Hard
  `#e58a4f`, Good `#9aac4a`, Easy `#639fd0`) so the label and chip also clear
  AA while hovered. Light hover already passed. The browser used for this
  pass reports `hover: none`, so hover colours were computed from the
  generated CSS values rather than captured with a pointer.

**Verification** (`rating-contrast-{light,dark}.json`, WCAG ratios):

| Button | Light label | Light chip | Dark label | Dark chip |
| --- | --- | --- | --- | --- |
| Again | 6.23 | 7.10 | 4.65 | 5.01 |
| Hard | 4.69 | 5.48 | 5.77 | 6.12 |
| Good | 4.68 | 5.44 | 6.12 | 6.56 |
| Easy | 6.36 | 7.21 | 4.86 | 5.33 |

The interval hint uses the same `text-on-accent` and measures the same as the
label. axe on `/review` with the answer shown reports zero `color-contrast`
violations in both themes (`axe/review-{light,dark}-after.json`), with the
screenshots `ratings-light.png` and `ratings-dark.png`.

## 4. Settings tab query parameter

**Repro before:** `/settings?tab=account` kept the URL but selected Scheduling.

**Change** (`apps/web/src/routes/_app/settings.tsx`):

- The route validates `tab` against the five known tabs and ignores anything
  else.
- `Tabs` is controlled by the search value (`scheduling` when absent).
- Switching tabs calls `navigate(..., { replace: true })`, so the URL updates
  without adding a history entry.

**Verification.**

- `/settings?tab=account` opened with Account selected and the Account panel
  visible (`screenshots/settings-account-tab.png`).
- Clicking Scheduling changed the URL to `/settings?tab=scheduling`; pressing
  Back returned to `/browse` rather than the previous tab.
- `/settings?tab=bogus` selects Scheduling, so a malformed value cannot leave
  every panel hidden.

## 5. Newly admitted review units were not appended to an open session

**Root cause.** The two review routes polled `armin.review.queue` through
TanStack Query. That helper calls `ConvexReactClient.query`, which returns the
client's local cached result when one exists and unsubscribes once its promise
resolves. A refetch shortly after a rating could therefore read the
pre-rating local snapshot: the sidebar's live `convexQuery` badge already
showed the new count, while the session stayed at `2 / 10`. A reload created a
fresh client and showed the admitted unit. The issue was in the queue fetch,
not in `reconcileSessionCards`: the merge already appends any incoming unit
that is not in the session and whose version is not older than a reviewed
occurrence.

The exact stale response was timing-dependent and did not recur
deterministically in this pass; the verification evidence (live sidebar count
new, session counter old) and the one-shot `ConvexReactClient.query` cache
behaviour identify it.

**Change** (`apps/web/src/routes/_app/review.tsx`,
`apps/web/src/routes/_app/deck.$deckId.review.tsx`):

- Both pages now use `convexQuery(api.review.queue, { ... , now })` under
  `useQuery`, the same live pattern the sidebar already uses. Every server
  queue result updates the TanStack cache, so an admitted unit reaches
  `reconcileSessionCards` without a poll or reload.
- `useNow()` advances the query arguments every 30 seconds, preserving the
  previous reason for re-evaluating due times without a data write. The
  explicit polling options and the now-redundant queue invalidation in the
  retry handler were removed.

**Verification.**

- All-decks `/review` with the test account: the subtitle changed from
  `7 review units due today` to `8 review units due today` when a new card was
  created through the API, with no reload or focus change
  (`live-append-before.png`, `live-append-after.png`, `live-append.txt`).
- Deck review on `qa-r2-eleven5` (cap raised to 11 so the unlocked dependent
  is admitted deterministically): rating the prerequisite Easy appended the
  dependent live, `3 / 10` → `4 / 11`, and the server queue contained
  `Eleven card 11` (`dependent-before.png`, `dependent-after.png`,
  `live-append.txt`).
- The two routes still typecheck and build, and the review smoke checks
  (reveal, four ratings, keyboard ratings, Undo) passed while running the
  walkthrough.
