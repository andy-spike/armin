## 1. Email failures were reported as success (major)

### Root cause

`sendEmail` throws `API key is not set` from the Resend component, but Better Auth wraps the
`sendVerificationEmail` / `sendResetPassword` callbacks in `runInBackgroundOrAwait`, which logs
`Failed to run background task` and still returns HTTP 200. The web pages only looked at the HTTP
result, so sign-up, unverified sign-in, and forgot-password all claimed a message had been sent.

### Change

- `packages/backend/convex/auth.ts`: when `RESEND_API_KEY` is absent, a `hooks.before` middleware
  rejects `/sign-up/email`, `/request-password-reset`, and `/send-verification-email` with HTTP 503
  and code `EMAIL_UNAVAILABLE` before an account or token is created for a flow that cannot finish.
  Existing verified accounts still sign in. `sendOnSignIn` is disabled in that state.
- `packages/backend/convex/auth.ts`: a production-only module-load warning reports a missing
  `RESEND_API_KEY` / Google credentials in deployment logs. Local development is intentionally
  quiet. `packages/backend/README.md` documents the resulting behaviour.
- `packages/backend/convex/account.ts`: new public `authFeatures` query returns whether email and
  Google are configured.
- `apps/web/src/routes/sign-up.tsx`, `forgot-password.tsx`, and
  `apps/web/src/components/auth/auth-layout.tsx`: show an up-front "Email isn't available" notice
  when the deployment cannot send, and surface the server error if a submit is attempted. An
  unverified sign-in no longer says "We just sent you a new link" when no provider exists.

### Verification

- Before the fix, sign-up with `qa-auth-fix-a@example.com` showed the false "We sent a verification
  link" screen while the server logged `Failed to run background task: [Error: API key is not set]`.
  Forgot-password for the sample account showed "a reset link is on its way" with the same log.
- After the fix, sign-up shows the notice and the submit returns "Email isn't available right now.
  Contact support." ([01](screenshots/01-signup-email-unavailable.png),
  [02](screenshots/02-signup-blocked-error.png)). Signing in with the address returned "Email or
  password is incorrect.", proving the blocked sign-up created no account.
- An existing unverified account now gets "Verify your email first. Email isn't available right now.
  Contact support." ([04](screenshots/04-signin-unverified-message.png)).
- Forgot-password shows the notice and the same submit error; no reset token is created.
- A production-style `SITE_URL` (`https://armin.example`) made `convex run account:authFeatures`
  print both deployment warnings; the real `SITE_URL` was restored immediately afterwards.
- Real provider delivery, domain verification, and Resend-side failures are out of scope; the
  remaining asynchronous delivery result is visible in Resend/deployment logs.

## 2. Post-login destination was lost (minor)

### Root cause

`_app`'s guard redirected to `/sign-in` without preserving the requested location, and the sign-in
and sign-up pages always redirected to `/`.

### Change

- `apps/web/src/routes/_app.tsx`: redirect to `/sign-in?redirect=<relative path>` including the
  original query and hash.
- `apps/web/src/lib/auth-client.ts`: `safeRedirectPath` accepts only same-origin relative paths
  (rejects absolute, protocol-relative, and backslash URLs).
- `sign-in.tsx` / `sign-up.tsx`: validate `redirect`, use it for the authenticated-user redirect,
  the password `callbackURL`, the Google `callbackURL`, and the final `window.location.assign`.

### Verification

- Signed out, `/settings?tab=account` redirected to
  `/sign-in?redirect=%2Fsettings%3Ftab%3Daccount`; signing in landed on
  `/settings?tab=account` with title `Settings · Armin`.
- `/deck/<id>/graph` → sign-in with `redirect=%2Fdeck%2F...%2Fgraph`; signing in landed on the graph
  ([05](screenshots/05-deeplink-graph-after-signin.png)). `/deck/<id>/review` returned to review.
- `/sign-in?redirect=https%3A%2F%2Fevil.com` and `?redirect=%2F%2Fevil.com` both canonicalized to a
  bare `/sign-in`, so they cannot redirect off-site.

## 3. "Password changed" and "Account deleted" notices never appeared (minor)

### Root cause

Two independent problems:

1. `validateSearch` accepted only `"1"`/`1`. TanStack Router runs search validation again on its own
   output while canonicalizing the URL, where `reset`/`deleted` are booleans, so the second pass
   returned `undefined` and redirected to a bare `/sign-in` (307), removing the parameter.
2. After a reset or deletion the session is revoked, but the short-lived Convex JWT still marked the
   page as authenticated; sign-in's guard then redirected to `/`, so the notice was lost even when
   the parameter survived.

### Change

- `apps/web/src/routes/sign-in.tsx`: accept `true` as well as `"1"`/`1`, and skip the
  authenticated-user redirect when a reset/deleted notice is present.
- `apps/web/src/routes/reset-password.tsx` keeps its existing `window.location.assign("/sign-in?reset=1")`;
  it now reaches a page that renders the notice. `apps/web/src/components/account-settings.tsx`
  keeps its `?deleted=1` redirect.

### Verification

- `/sign-in?reset=1` and `/sign-in?deleted=1` now canonicalize to `?reset=true` / `?deleted=true` and
  render the notices ([03](screenshots/03-signin-reset-notice.png)).
- A real password reset was exercised with an existing local reset token: after saving a new
  password, the app redirected to `/sign-in?reset=true` with "Password changed. Sign in with your
  new password." and the new password worked. The sample password was restored to `armin1234`
  afterwards and verified by signing in.
- Immediately after that reset, the stale Convex JWT no longer bounced the notice page to `/`; the
  same state was checked with `?deleted=1`.

## 4. Google buttons failed silently when OAuth was unconfigured (minor)

### Root cause

The buttons were always rendered; the backend had no client ID/secret, so `/sign-in/social` and
`/link-social` returned HTTP 500 `CLIENT_ID_AND_SECRET_REQUIRED`, and the UI ignored the error.

### Change

- Backend exposes `authFeatures.google`; Google provider config is omitted when both credentials
  are absent.
- `sign-in.tsx` / `sign-up.tsx` render the Google button and divider only when Google is configured.
- `account-settings.tsx` shows "Not configured" and a configuration hint instead of the Link button,
  and wraps `linkSocial` in a toast-producing mutation for failures when Google is configured.

### Verification

- Sign-in and sign-up show only the email form, with no Google button and no "or" divider.
- Settings → Account shows "Google sign-in isn't configured for this deployment." and "Not
  configured" ([06](screenshots/06-settings-google-not-configured.png)).
- No `/sign-in/social` request is made from the UI; the server no longer warns per request because
  the provider is absent. Real Google credentials remain out of scope.

## 5. Duplicate-email sign-up copy promised a link (minor)

### Root cause

The anti-enumeration duplicate path returns a fake success with no email, while the copy said a link
had been sent.

### Change

`sign-up.tsx` success copy is now "If this email can be used to create an account, we've sent a
verification link to …". The resend notice is hedged the same way. Anti-enumeration behaviour is
unchanged.

### Verification

With a temporary dummy `RESEND_API_KEY` (removed afterwards), signing up with the existing
`test@example.com` showed the neutral copy ([08](screenshots/08-signup-duplicate-neutral-copy.png))
and created no second account. With the real deployment state (no provider), sign-up is blocked
before the duplicate path, as described in issue 1.

## 6. Every route had the title "Armin" (minor)

### Change

One `head` title per page route:

| Route | Title |
| --- | --- |
| `/` | Decks · Armin |
| `/browse` | Browse · Armin |
| `/review` | Review · Armin |
| `/settings` | Settings · Armin |
| `/deck/<id>` | Deck · Armin (static fallback; deck name is not in the route head) |
| `/deck/<id>/graph` | Graph · Armin |
| `/deck/<id>/review` | Deck review · Armin |
| `/sign-in` | Sign in · Armin |
| `/sign-up` | Create account · Armin |
| `/forgot-password` | Reset password · Armin |
| `/reset-password` | Choose a new password · Armin |
| unmatched URL | Page not found · Armin |

The 404 title is rendered by `__root.tsx`'s `notFoundComponent` (React hoists its `<title>`); the
root `head` remains the fallback.

### Verification

Read from the running browser: `/` → `Decks · Armin`, `/browse` → `Browse · Armin`, `/review` →
`Review · Armin`, `/settings` → `Settings · Armin`, deck → `Deck · Armin`, graph → `Graph · Armin`,
deck review → `Deck review · Armin`, sign-in → `Sign in · Armin`, sign-up → `Create account · Armin`,
forgot → `Reset password · Armin`, reset → `Choose a new password · Armin`, unmatched →
`Page not found · Armin` ([07](screenshots/07-page-not-found.png)). Navigating 404 → Browse → 404
updated the title each time.
