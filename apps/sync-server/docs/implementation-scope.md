# First sync implementation

This is the scope produced by the grill-with-docs session. Product decisions are
settled. The engineering defaults below are proposed for final confirmation;
implementation has not started.

## Deliverable

A locally runnable sync server with integration tests and Cloudflare deployment
configuration. Desktop and mobile integration, live Google setup, and deployment
are separate work. The intended beta supports separate Accounts, open Google
registration, and no billing or invitations.

## Product decisions

- Each Account synchronizes one Profile. Other local Profiles remain local.
- The first device initializes an empty Account from one selected local Profile,
  including its content, review history, calculated schedules, settings, and media.
- A device joining an Account with data downloads into a new local Profile.
  Existing local Profiles remain untouched. Collections are not merged automatically.
- Synchronize Decks, Flashcards, tags, prerequisite links, graph positions,
  archive state, Flashcard media, Review-unit progress, and review history.
- Synchronize all Profile settings, including keyboard shortcuts and per-Deck
  study overrides.
- Clients calculate schedules. The server stores them without replaying reviews
  or running FSRS.
- For competing content edits, edit-versus-delete operations, and reviews based
  on the same older version, accept the first valid change and return a conflict
  for the other. The client preserves its rejected pending change for resolution.
- A Deck's prerequisite graph is one versioned record. Validate the complete
  submitted graph and reject an older graph version instead of merging links.
- Review undo restores the schedule and removes the latest review together.
  Require the expected progress version and latest review; reject stale undo.
- Keep sync change entries and deletion records throughout the beta. Do not add
  cleanup or expired-sync-position recovery in this implementation. These entries
  are separate from the user's review history.
- Use HTTPS and provider-managed encryption at rest. The service can access data
  contents. There are no client-managed Profile encryption keys.

## Proposed engineering defaults

### Runtime and authentication

Use one TypeScript Cloudflare Worker with D1 and private R2 bindings. Better Auth
runs Google sign-in and session routes in the same Worker, using its native D1
support. Store authentication and sync tables in the same D1 database. Use
prepared SQL and checked-in migrations, applied by Wrangler; no ORM is required.

Use Better Auth's normal cookie sessions and session lookup for protected routes.
Derive ownership from the authenticated Better Auth user ID. Better Auth's
`account` table represents a linked login method, not an Armin Account. Do not add
a custom JWT system, email/password login, or native-client plugins in this step.

Set an explicit auth base URL, trusted origins, and required secret names. Enable
Workers Node compatibility. Document Google credentials and the callback URL for
later deployment without requiring live credentials for local integration tests.

Better Auth supports [native D1](https://better-auth.com/blog/1-5),
[cookie sessions](https://better-auth.com/docs/concepts/session-management), and
[test fixtures](https://better-auth.com/docs/plugins/test-utils).

### Record identity and writes

Preserve existing Deck, Flashcard, Review-unit, and review-log UUIDs during the
initial upload and later downloads. Clients joining a synced Profile adopt its
record IDs rather than independently generating a second set of Review units.
Validate each Review unit's Flashcard relationship and stable `subKey`.

Use typed change requests and versioned request/response schemas in
`packages/sync-contract`. The server validates record shape and relationships;
it does not generate Review units or calculate study behavior. Derived lock and
display state is regenerated by clients rather than used as authoritative sync
state.

A content change that creates or removes Review units is an atomic group with
its required related changes. A review or undo includes the expected Flashcard
content version as well as the progress version, preventing stale reviews from
recreating removed units. Deck membership changes and deletions must preserve
prerequisite-graph validity in the same accepted operation.

Save accepted data, record versions, mutation outcomes, and change entries
atomically. Unique mutation IDs make retries return their previous result.
Conflict responses include enough accepted state for later client resolution;
the server does not provide the conflict UI or automatic merge rules.

### Uploads and downloads

Provide initial Profile upload, current-state download, change push, and
paginated change pull operations. Use server sequence numbers as sync positions,
not device timestamps. A new device receives a consistent current-state download
and matching position, then pulls later changes. Version the protocol explicitly.

Initial upload must tolerate retries and interruptions, must not publish an
incomplete Profile as ready, and must not overwrite an already initialized
Account. Ordinary writes must not expose partially accepted related changes.

Use existing Profile-relative media references and content-addressed filenames.
Keep the existing 25 MiB per-file limit. Scope R2 keys and access to the Account
and synced Profile. Upload and verify media before accepting records that
reference it. Stream transfers through the Worker initially; presigned uploads
and media garbage collection are deferred. Database changes and R2 writes do not
share a transaction, so retries must tolerate already stored media.

There are no WebSockets, Durable Objects, Queues, KV caches, or scheduled jobs.
Sync timing and durable client pending-change capture belong to later client
integration. Existing client timestamps alone cannot detect every edit.

### Workspace and deployment configuration

Add the server workspace with pnpm scripts for local development, typechecking,
linting, tests, binding types, and local/remote migrations. Add a health endpoint,
Wrangler configuration, ignored local secret files, and a setup README.

Use local D1/R2 for development and integration tests. Include explicit staging
and production configuration templates with separate resource names and required
secrets. Do not provision resources or deploy as part of this deliverable.

## Acceptance tests

Use the Workers runtime with local D1 and R2, checked-in migrations, and real
Better Auth session fixtures. Test through the protected request interface.

- Two Accounts remain isolated across sync and media requests. Missing, expired,
  and revoked sessions cannot access data.
- An existing Profile initializes once, including history, schedules, settings,
  graphs, and media. Retrying or interrupting initialization is safe.
- A second simulated device downloads consistent state and catches up through
  paginated changes without omissions or duplicate effects.
- Independent record edits succeed. Competing edits, edit-versus-delete changes,
  and stale reviews return conflicts without partially applying their writes.
- A review saves its log and schedule together. Undo removes the latest log and
  restores its schedule together; stale undo and review of removed units fail.
- Graph changes reject stale versions, cycles, and cross-Deck links. Related
  content changes preserve relationships and do not leave dangling progress.
- Deletions propagate after long offline periods. Settings include keyboard
  shortcuts, and media can be uploaded and retrieved only by its owning Account.

Tests simulate two devices at the server interface. They do not prove desktop or
mobile sync integration or real Google OAuth. Those checks follow in their own
implementation and deployment steps.

## Scope exclusions

- Desktop/mobile changes, including local change capture, conflict UI, sign-in
  screens, device callbacks, and secure session storage.
- Real Google OAuth configuration or smoke tests, Cloudflare provisioning, and
  live staging/production deployment.
- Multiple synced Profiles per Account, automatic merging, server-side FSRS,
  billing, invitations, log cleanup, and media garbage collection.

## Repository facts behind the design

- Mobile is currently a starter screen with no persistence or review flow.
- Local Profiles have separate databases; restoration creates a new local
  Profile ID while preserving record IDs inside the database.
- Desktop rating already saves a calculated schedule and review log together.
  Undo restores the schedule and deletes the latest log. There is no review
  replay system.
- Review units have random UUIDs and a stable `subKey` within their Flashcard.
  Content changes can create or remove them.
- Independent prerequisite edits can combine into a cycle. Record version checks
  alone cannot protect the graph.
